# AHT redesign: a nightly regression suite for after MVP launch

Date: 14 November 2026. Main `897117b` (#1858). Design and coverage map only: no product file, live run, deployment, migration, Stripe or production change. Row-by-row map: [`coverage-map.v1.json`](coverage-map.v1.json).

## Framework (Akin, 14 Nov)

There is no target count. Each live case is a full user journey, oriented to MVP launch, run nightly after launch so that an upgrade that breaks something is caught. Every area is covered end to end, billing included. No test exists just to have a test: a check stays live only when a faster test can't catch the same break.

## The short version

- **9 journeys replace the 15 cases.** Two are new: a paying customer's billing lifecycle (J2) and an existing customer after an upgrade (J9). Neither exists today, and both are what a nightly regression run is for.
- **All 204 catalog checks have a home.** 179 move unchanged, 10 move from AHT-15 onto a run-owned account, 7 are strengthened, and 8 AHT-03 rows are consolidated because the same check already runs on the same code in J1 and J3. 15 new checks cover short Stop, the payment wall, paid access, deletion and upgrade continuity.
- **Every gap and every 14 Nov failure or hold is mapped** to a live leg or a named faster test (§4, §5). Nothing is closed by moving it: a faster test counts only once it fails on the deliberately broken behaviour and passes when restored.
- **The suite can't run nightly yet.** Besides the product fixes, three things in the harness make a nightly run HOLD by design after an upgrade (§6, items 9 to 11). They need fixing for the suite to do its job.
- **8 fresh signups per night instead of 14**, plus one long-lived account (J9). Counted, not timed.

### Notes per journey

- **J1** order matters: expiry is the last practice leg because it ends service, and deletion follows it. The trial is ended by the service role on the run-owned account only (`trial_expires_at` in the past, never `commercial_trial_granted_at`, never another account). Under Akin's rule the expired account sees no history, so `history-preserved` runs in J1.d before expiry.
- **J2** reuses the existing `stripe-paid-soft-launch-runtime` spec's checkout, portal and downgrade steps, but takes entitlement from the real webhook rather than a synthetic post, and adds the wall, restored history and paid deletion. It runs only where Stripe is in test mode (open question 1). Kept separate from J1 so a Stripe outage can't hide a practice regression.
- **J3** drops AHT-03's copies of repeat, next-start, numeric and probe-save rows (same code, already in J1 and J3.a). The partial fixture's unique value is `focus-not-detected-explained` and the coverage count on missed points.
- **J5.a** runs first in its own fresh context so the model cache is cold. Until #1858 is deployed and J5.a has passed once, dispatch it alone so a known failure doesn't share a run.
- **J7** shares one signup across three fresh contexts. Each leg asserts its own take by session id, so the one saved take from an earlier leg can't satisfy a later one.
- **J8** depends on the feedback fence (#1859) and its runner wiring (#1860).
- **J9** is read-mostly: one take, no signup, no checkout. It is the leg that answers Akin's example directly.

## 7. Recommended count: 9

Nine because there are nine distinct things that can break for a customer and need a real browser to see: first use through the wall, paying, Focus, a bad save connection, leaving mid-flow, two places, first-time setup failures, feedback, and existing data after an upgrade. Fewer would put unrelated stories in one run, so one failure (a Stripe outage, a cold-start bug) would hide the others. More would repeat signup and model download for no new signal: Sam's ten splits 12, 13 and 14 into separate runs, but they share setup safely with fresh contexts, and his set has no billing lifecycle or upgrade continuity journey.
