# AHT redesign: a nightly regression suite for after MVP launch

Date: 14 November 2026. Main `897117b` (#1858). Design and coverage map only. Row-by-row map: [`coverage-map.v1.json`](coverage-map.v1.json), regenerated from the catalog by [`build_map.py`](build_map.py) (`python3 docs/aht-nightly/build_map.py . docs/aht-nightly/coverage-map.v1.json`). Given a third output path and #1862's `mapping.json`, it also writes the design in #1862's `speaksharp.aht-rationalization.v1` schema, keeping #1862's candidate fast tests, so that PR's validator (`tools/aht-rationalization/validate.mjs`) checks this design too. The schema has no field for strengthened or new rows, so the export lists them under `additionalRequirements`.


## Framework (Akin, 14 Nov)

There is no target count. Each live case is a full user journey, oriented to MVP launch, run nightly after launch so that an upgrade that breaks something is caught. Every area is covered end to end, billing included. No test exists just to have a test: a check stays live only when a faster test can't catch the same break. A check leaves the live suite only with reviewed proof that its replacement fails on the same break and passes when restored; until then it stays live.

## The short version

- **9 live journeys replace the 15 cases.** Two are new: the payment wall and checkout on production (J2), and an existing paying customer after an upgrade (J9).
- **Billing's full lifecycle is not an AHT.** The subscription suite (#1795, `tests/billing/user-journey/`) covers conversion, failed renewal and recovery, and cancellation to period end with real Stripe events in a test-mode sandbox, on its own schedule. The live J2 covers only what production adds.
- **Every catalog check has a home** (§2): most move unchanged, AHT-15's move onto a run-owned account and a few are strengthened. None is demoted: a row leaves the live suite only with reviewed replacement proof. New checks cover the trial's length, short Stop, sign-out reads, the payment wall, checkout, deletion, feedback with no session and upgrade continuity.
- **Every known gap has a home** (§3, §4): a live leg or a named faster test. A faster test counts only once it fails on the deliberately broken behaviour and passes when restored.
- **Each run has a hard budget** (§6): at most 31 coaching requests across the nine journeys; past that the run sends no more and the rest reports NOT RUN, never a pass.
- **Prerequisites, open decisions and run results are tracked in the PR and issues**, not in this design, so it doesn't go stale as they land.

## 1. The journeys

Every leg keeps its own rows and cleanup. The four invariants (`owner-bound`, `start-press-budget`, `no-cloud-stt`, `owned-pages-closed`) are asserted in every leg.

**Dependent legs.** A leg that needs an earlier leg's result is NOT RUN, not FAIL, when that leg failed: J1.b to J1.d need J1.a's take, J1.f needs J1.e's expiry, and J8.c needs J8.b's takes. J1.e needs only the account, so it runs even when J1.a failed. Every other leg is independent of the legs before it.

### Notes per journey

- **J1.** Expiry is the last practice leg because it ends service; deletion follows it. `history-preserved` runs in J1.d, before expiry, because the expired account sees no history under Akin's rule. Ending the trial early is a production write, approved by the product owner on 14 Nov for accounts the test created and tagged, and no others. The tag is the run-owned account's server-issued `app_metadata.canary` claim, set by `markRunOwnedAccountCanary` after its prefix and UID/email cross-check, and only when the run has `RWT_CANARY_CLAIM_ACK` set (without it J1.e, J1.f and J2 are NOT RUN); the write refuses an account without it (fail closed), checks the exact account id, ends the trial on that account only (`trial_expires_at` in the past, never `commercial_trial_granted_at`, never another account), and cleanup removes the account. J1 doesn't wait out the trial, so the trial's length is checked at signup instead: J1.a reads the account's own profile with its own token, no service-role read, and asserts on the deployed build that the trial started within the signup window and ends exactly 30 days later (product owner, 14 Nov). The DB `trial-journey` test checks 30 days only on the original 1282 trigger body, not the shipped one, so this row is the check on the shipped chain until G8's guard lands. The wall offers deletion without promoting it, and no History, PDF or export first. The wall is checked twice: on the still-open session (reload and navigate, as a real user who never signs out would see it) and after a fresh sign-in. `trial-expired-server-refuses` calls the deployed endpoints directly with the account's own token. It doesn't duplicate the DB and contract tests: it checks that the deployed bodies refuse. J1 also needs #1858 deployed: the cancelled-load watchdog stopped an AHT-01 run as well as AHT-04.
- **J2.** Its expired account goes through the same tagged, fail-closed trial-ending write as J1. It never completes a payment, so production takes no charge, but it is not free of side effects. Opening Checkout on production creates a live-mode Checkout Session for the run-owned email and writes checkout rows (`begin_account_checkout`, `record_account_checkout`) that don't cascade on account deletion, and an abandoned session stays payable until it expires. J2 stays disabled until a reviewed cleanup step expires the session through Stripe, settles the checkout operation through the existing RPCs and proves nothing is left. Conversion, a failed renewal and recovery, cancellation to period end, and deleting a paying account belong to #1795's suite in a sandbox (§3). #1795's `portal_expiry` journey asserts readable saved history after expiry, which the 14 Nov rule now forbids; it has to change with the requirements doc.
- **J3.** AHT-03 keeps all its rows on the partial fixture. Its rapid repeat, next start, numeric and probe-save rows repeat checks in J1 and J3.a, but they stay live until proof shows another check fails on the same break: AHT-03's `probe-save-isolation` is the row that failed on 14 Nov. Its `same-target-repeat` and `analytics-repeat-opens-product` are the only repeat that starts from a take with missed points. J3 also depends on the feedback fence, because AHT-02 writes feedback.
- **J5.a** runs first in its own fresh context so the model cache is cold. Between legs the lease is released and verified, and interceptors and drafts are reset, so a lease left by the cold-Start leave can't block J5.b's Start. Until #1858 is deployed and J5.a has passed once, dispatch it alone so a known failure doesn't share a run. J5.c keeps both observers the gap ledger requires for GAP-05 (R5, and R4C with the same leave action) and reports the tab-close variant separately.
- **J7** shares one signup. The denial leg (J7.a) needs its own browser launch, because the deny flag is set at launch for the whole browser; it signs in again to the same account. Whether the microphone can then be granted inside that launch is still unqualified, so J7.a stays HOLD until it is. J7.b and J7.c each run in a fresh context with a cold model cache. Each leg asserts its own take by session id, so a take from an earlier leg can't satisfy a later one. The harness already refuses AHT-12 and AHT-14 until a same-context denial-then-grant and a bytes-received fault are qualified; those qualifications are what's missing, not the checks. J7.d deletes the account through the product during the trial, the common path; run cleanup still verifies nothing is left.
- **J8** depends on the feedback fence (#1859) and its runner wiring (#1860).
- **J9** reads only. It doesn't record, because transcript retention keeps only the newest session's transcript, and nightly takes would erode its history and grow the account past adapter limits. The account signs up and pays through the product once, as a customer would, and records its sessions through the product on a named earlier release; nothing is seeded into the database, and its history is kept from then on. As a real subscription on production, it renews at $10 a month. Its billing check only asserts that the portal opens; it takes no action there and never records the portal's address, because a portal session works for anyone who holds the link. A new take after an upgrade is already covered by J1 to J8. J9 does not cover a browser tab left open across a deploy (stale code chunks, or a model cached by the old release). That needs a check around each release (§4), because a nightly run starts with a clean browser.

## 5. Recommended count: 9 live journeys

Nine because there are nine distinct things that can break for a customer and need a real browser on the deployed build:
1. First use through the wall.
2. Getting from the wall to payment.
3. Focus.
4. A bad save connection.
5. Leaving mid-flow.
6. Two places at once.
7. First-time setup failures.
8. Feedback.
9. Existing data after an upgrade.

Fewer would put unrelated stories in one run, so one failure, like a Stripe outage or a cold-start bug, would hide the others. More would repeat signup and model download for no new signal. #1862's ten-scenario grouping keeps AHT-04, 12, 13 and 14 as separate runs. Here they are legs of J5 and J7: the mic denial in its own deny-launched browser, the model faults in fresh contexts with cold caches, and resets between legs, so every distinct browser condition #1862 names is kept while signup is shared. #1862 proves expiry, the wall, deletion and paid restoration inside its first journey; here paid restoration is proven in #1795's sandbox suite, and J2 and J9 add checkout on production and an existing customer after an upgrade. The billing lifecycle is real coverage but not an AHT: it runs in a sandbox, on #1795's existing suite.

## 6. Run budget

A run is the smallest one that still proves every journey. The paid calls in a run are coaching requests: every take transcribes in the browser (`no-cloud-stt`), so recording costs runtime and the model download (about 80 MB from our own origin per cold context, roughly 1 GB a night) but no transcription service. The maxima come from the existing per-case `coaching request budget` rows, one request per saved take; the run also has at least 31 takes and 42 Start presses, the catalog's minimums:

| Journey | Coaching requests, at most | Fresh signups |
|---|---|---|
| J1 | 4 | 1 |
| J2 | 0 | 1 |
| J3 | 11 (7 full Focus, 4 partial) | 1 |
| J4 | 4 | 1 |
| J5 | 5 | 1 |
| J6 | 2 | 1 |
| J7 | 3 | 1 |
| J8 | 2 | 1 |
| J9 | 0 | 0 (long-lived) |
| **Run** | **31** | **8** |

- A journey that sends more than its maximum fails its budget row, as today.
- The run stops at 31 coaching requests, with no margin, because the product owner asked for the least cap possible and any request past 31 means some journey already went over its own maximum. Once it is reached the harness sends no more, and every leg that still needed coaching reports NOT RUN, never PASS, so the run can't be green.
- Each coaching request can make up to 3 provider calls (`MAX_PROVIDER_ATTEMPTS`), so the provider ceiling is 93 calls. The dollar cap is 93 times the provider's price per call, set when the schedule is enabled.
- A request the server refuses before any provider work, like J1.e's expired-token coaching call, costs nothing and sits outside the ceiling. If the server wrongly accepts it, it counts against the ceiling and fails its row.
- Deleting an account through the product sends a sign-in email, so J1.f and J7.d send two auth emails a run and need a mailbox the harness can read for each run-owned address. Supabase's default mail has a low hourly limit, and a custom mail provider may cost money.
- J2 opens one Checkout Session and takes no charge. J9's $10 a month is a standing cost, not a per-run one.
- The ceiling falls whenever a row leaves the live suite with reviewed proof, because its takes go with it.
