# AHT redesign: a nightly regression suite for after MVP launch

Date: 14 November 2026. Main `897117b` (#1858). Design and coverage map only. Row-by-row map: [`coverage-map.v1.json`](coverage-map.v1.json), regenerated from the catalog by [`build_map.py`](build_map.py) (`python3 docs/aht-nightly/build_map.py . docs/aht-nightly/coverage-map.v1.json`). Given a third output path and #1862's `mapping.json`, it also writes the design in #1862's `speaksharp.aht-rationalization.v1` schema, keeping #1862's candidate fast tests, so that PR's validator (`tools/aht-rationalization/validate.mjs`) checks this design too. The schema has no field for strengthened or new rows, so the export lists them under `additionalRequirements`.


## Framework (Akin, 14 Nov)

There is no target count. Each live case is a full user journey, oriented to MVP launch, run nightly after launch so that an upgrade that breaks something is caught. Every area is covered end to end, billing included. No test exists just to have a test: a check stays live only when a faster test can't catch the same break. A check leaves the live suite only with reviewed proof that its replacement fails on the same break and passes when restored; until then it stays live.

## The short version

- **9 journeys replace the 15 cases: eight on the deployed production build and J9 on the billing sandbox.** Two are new: the payment wall and checkout on production (J2), and an existing paying customer after an upgrade (J9, paid in Stripe test mode only, so it runs against a persistent billing sandbox, all its results are sandbox-only, and it is disabled until that sandbox exists).
- **Billing's full lifecycle is not an AHT.** The subscription suite (#1795, `tests/billing/user-journey/`) is where conversion, failed renewal and recovery, and cancellation to period end are to be proven, with real Stripe events in a test-mode sandbox on its own schedule. It is not runnable yet: the sandbox target is unconfigured and no schedule exists, so only a real sandbox run will prove them. The live J2 covers only what production adds.
- **Every catalog check has a home** (§2): most move unchanged, AHT-15's move onto a run-owned account and a few are strengthened. None is demoted: a row leaves the live suite only with reviewed replacement proof. New checks cover the trial's length, short Stop, sign-out leaks and stale requests, the payment wall, checkout, deletion, feedback with no session and upgrade continuity.
- **Every known gap has a home** (§3, §4): a live leg or a named faster test. A faster test counts only once it fails on the deliberately broken behaviour and passes when restored.
- **Each run has a proposed hard budget** (§6): at most 31 coaching requests, calculated as the minimum that still gives a truthful signal under the product owner's rule, enforced per journey; past a journey's maximum it sends no more and its remaining coaching legs report NOT RUN, never a pass.
- **Prerequisites, open decisions and run results are tracked in the PR and issues**, not in this design, so it doesn't go stale as they land.

## 1. The journeys

Every leg keeps its own rows and cleanup. The four invariants (`owner-bound`, `start-press-budget`, `no-cloud-stt`, `owned-pages-closed`) are asserted in every leg.

**Dependent legs.** A leg that needs an earlier leg's result is NOT RUN, not FAIL, when that leg failed: J1.b to J1.d need J1.a's take, J1.f needs J1.e's expiry, and J8.c needs J8.b's takes. J1.e needs only the account, so it runs even when J1.a failed. Every other leg is independent of the legs before it.

### Notes per journey

- **J1.** Expiry is the last practice leg because it ends service; deletion follows it. `history-preserved` runs in J1.d, before expiry, because the expired account sees no history under Akin's rule. Ending the trial early is a production write, approved by the product owner on 14 Nov for accounts the test created and tagged, and no others. The tag is the run-owned account's server-issued `app_metadata.canary` claim, set by `markRunOwnedAccountCanary` after its prefix and UID/email cross-check, and only when the run has `RWT_CANARY_CLAIM_ACK` set (without it J1.e, J1.f and J2 are NOT RUN); the write refuses an account without it (fail closed), checks the exact account id, ends the trial on that account only (`trial_expires_at` in the past, never `commercial_trial_granted_at`, never another account), and cleanup removes the account. J1 doesn't wait out the trial, so the trial's length is checked at signup instead: J1.a reads the account's own profile with its own token, no service-role read, and asserts on the deployed build that the trial started within the signup window and ends exactly 30 days later (product owner, 14 Nov). The DB `trial-journey` test checks 30 days only on the original 1282 trigger body, not the shipped one, so this row is the check on the shipped chain until G8's guard lands. The wall offers deletion without promoting it, and no History, PDF or export first. The wall is checked twice: on the still-open session (reload and navigate, as a real user who never signs out would see it) and after a fresh sign-in. `trial-expired-server-refuses` calls the deployed endpoints directly with the account's own token. It doesn't duplicate the DB and contract tests: it checks that the deployed bodies refuse. J1 also needs #1858 deployed: the cancelled-load watchdog stopped an AHT-01 run as well as AHT-04.
- **J2.** Its expired account goes through the same tagged, fail-closed trial-ending write as J1. It never completes a payment, so production takes no charge, but it is not free of side effects. Opening Checkout on production creates a live-mode Checkout Session for the run-owned email and writes checkout rows (`begin_account_checkout`, `record_account_checkout`) that don't cascade on account deletion, and an abandoned session stays payable by whoever holds its address until it expires, so that address is never written to logs, Playwright traces, HAR files, screenshots or run receipts. J2 stays disabled until a reviewed cleanup step expires the session through Stripe and reconciles every outstanding checkout operation to a settled state through the existing RPCs, keeping the audit records the billing code needs; it doesn't delete billing rows. Conversion, a failed renewal and recovery, cancellation to period end, and deleting a paying account belong to #1795's suite in a sandbox (§3). #1795's `portal_expiry` and `refund_period_end` steps hold `history_retained` and `access_expired` as PENDING_POLICY, never asserted; once the requirements carry the 14 Nov rule, they can assert no access instead. Configuring the sandbox and checking its readiness is separate from running the lifecycle there: only a real sandbox run proves conversion, renewal and cancellation.
- **J3.** AHT-03 keeps all its rows on the partial fixture. Its rapid repeat, next start, numeric and probe-save rows repeat checks in J1 and J3.a, but they stay live until proof shows another check fails on the same break: AHT-03's `probe-save-isolation` is the row that failed on 14 Nov. Its `same-target-repeat` and `analytics-repeat-opens-product` are the only repeat that starts from a take with missed points. J3 also depends on the feedback fence, because AHT-02 writes feedback.
- **J5.a** runs first in its own fresh context so the model cache is cold. Between legs the lease is released and verified, and interceptors and drafts are reset, so a lease left by the cold-Start leave can't block J5.b's Start. Until #1858 is deployed and J5.a has passed once, dispatch it alone so a known failure doesn't share a run. J5.c keeps both observers the gap ledger requires for GAP-05 (R5, and R4C with the same leave action) and reports the tab-close variant separately.
- **J7** shares one signup. The denial leg (J7.a) needs its own browser launch, because the deny flag is set at launch for the whole browser; it signs in again to the same account. Whether the microphone can then be granted inside that launch is still unqualified, so J7.a stays HOLD until it is. J7.b and J7.c each run in a fresh context with a cold model cache. Each leg asserts its own take by session id, so a take from an earlier leg can't satisfy a later one. The harness already refuses AHT-12 and AHT-14 until a same-context denial-then-grant and a bytes-received fault are qualified; those qualifications are what's missing, not the checks. J7.d deletes the account through the product during the trial, the common path; run cleanup still verifies nothing is left.
- **J8** depends on the feedback fence (#1859) and its runner wiring (#1860).
- **J9** records no takes, because transcript retention keeps only the newest session's transcript, and nightly takes would erode its history and grow the account past adapter limits. The account signs up and pays through the product once, as a customer would, with a Stripe test-mode card, and records its sessions through the product on a named earlier release; nothing is seeded into the database, and its history is kept from then on. It still isn't free of side effects: opening the billing portal creates a Stripe portal session, and that session's address works for anyone who holds it, so the check only asserts the portal opens, takes no action there and never writes the address to logs, Playwright traces, HAR files, screenshots or run receipts. No test account is ever charged for real (product owner, 14 Nov 16:36Z: "no real charge"), and production's checkout takes live keys, so J9 runs against the billing sandbox in Stripe test mode, not production. The sandbox has to be upgraded to each release for J9 to test an upgrade, and #1795's sandbox creates and removes its accounts on each run, so J9 needs its own persistent sandbox that keeps the account across releases and is upgraded with each one; J9 stays disabled until that exists. J9 has two legs. J9.a runs on that sandbox, and every result is labelled "Stripe test-mode sandbox: not production billing proof"; it never stands as proof of production billing or of production data after an upgrade. J9.b is whether a real paid account keeps its entitlement and data after a production upgrade (`production-entitlement-after-upgrade`), reported NOT RUN on every run until there is a safe, approved way to prove it. Opening the kept sessions must send no coaching request (`old-sessions-no-new-coaching`, budget 0): a request would mean the stored coaching no longer reads after the upgrade. Setup checks before the release that every kept session has stored coaching and reports HOLD if one doesn't, so a session whose coaching never stored can't blame the upgrade. A new take after an upgrade is already covered by J1 to J8. J9 does not cover a browser tab left open across a deploy (stale code chunks, or a model cached by the old release). That needs a check around each release (§4), because a nightly run starts with a clean browser.

## 5. Recommended count: 9 journeys

Nine because there are nine distinct things that can break for a customer and need a real browser on a deployed build (the deployed production build for eight, and the billing sandbox for J9, which can't hold a real paid account):
1. First use through the wall.
2. Getting from the wall to payment.
3. Focus.
4. A bad save connection.
5. Leaving mid-flow.
6. Two places at once.
7. First-time setup failures.
8. Feedback.
9. Existing data after an upgrade.

Fewer would put unrelated stories in one run, so one failure, like a Stripe outage or a cold-start bug, would hide the others. More would repeat signup and model download for no new signal. #1862's ten-scenario grouping keeps AHT-04, 12, 13 and 14 as separate runs. Here they are legs of J5 and J7: the mic denial in its own deny-launched browser, the model faults in fresh contexts with cold caches, and resets between legs, so every distinct browser condition #1862 names is kept while signup is shared. #1862 proves expiry, the wall, deletion and paid restoration inside its first journey; here paid restoration is to be proven by a real sandbox run of #1795's suite (not yet runnable), and J2 and J9 add checkout on production and an existing customer after an upgrade. The billing lifecycle is real coverage but not an AHT: it runs in a sandbox, on #1795's existing suite.

## 6. Run budget

A run is the smallest one that still proves every journey. The paid calls in a run are coaching requests: every take transcribes in the browser (`no-cloud-stt`), so recording costs runtime and the model download (about 80 MB from our own origin per cold context, roughly 1 GB a night) but no transcription service. The review of each saved take sends one coaching request (`get-ai-suggestions`, in `AISuggestions.tsx`), and the existing `coaching request budget` rows allow at most one per saved take, so a journey's coaching requests equal the saved takes its rows need. The counts below are those saved takes (each case's catalog `minimumTakes`), which is also each case's current maximum; the run also has at least 31 takes and 43 Start presses (the catalog's 42 plus J1.c's short-Stop take):

| Journey | Coaching requests, at most | Fresh signups |
|---|---|---|
| J1 | 4 | 1 |
| J2 | 0 | 1 |
| J3 | 11 (7 full Focus, 4 partial) | 1 |
| J4 | 4 | 1 |
| J5 | 5 | 1 |
| J6 | 2 | 1 |
| J7 | 3 | 1 |
| J8 | 2 | 1 |
| J9 | 0 | 0 (long-lived) |
| **Run** | **31** | **8** |

- A journey that sends more than its maximum fails its budget row, as today.
- The product owner's rule (14 Nov 16:36Z) is the least cap that still gives a truthful signal. For these nine journeys that is 31 coaching requests, with no margin: it is the sum of the saved takes the kept rows need, so a lower cap would leave some row's take unsent and that leg NOT RUN by design. 31 is a calculated proposal for the chosen journeys, not a fixed requirement: it falls whenever a row leaves the live suite with reviewed proof.
- The cap counts one request per saved take, only for legs that can run that night: 31 when every leg runs, 30 while J7.a is on hold. It may be set lower, which turns the uncovered legs NOT RUN, never higher.
- The cap is enforced per journey, at each journey's maximum above, not as one shared pool. An automatic coaching retry (the review retries a recoverable failure once, and GAP-01 is still open) fails that journey's budget row, but it can't use up another journey's allowance and turn an unrelated leg NOT RUN. Once a journey reaches its maximum the harness sends no more for it, and every leg of it that still needed coaching reports NOT RUN, never PASS, so the run can't be green.
- Reopening a take whose coaching is stored sends no request; the page reads the stored review. J9 opens only kept sessions, so its maximum is 0.
- Each coaching request can make up to 3 provider calls (`MAX_PROVIDER_ATTEMPTS`), so the provider ceiling is 93 calls. The dollar cap is 93 times the provider's price per call, set when the schedule is enabled.
- A request the server refuses before any provider work, like J1.e's expired-token coaching call, costs nothing and sits outside the ceiling. If the server wrongly accepts it, it counts against the ceiling and fails its row.
- Deleting an account through the product sends a sign-in email, so J1.f and J7.d send two auth emails a run and need a mailbox the harness can read for each run-owned address. Supabase's default mail has a low hourly limit, and a custom mail provider may cost money.
- J2 opens one Checkout Session and takes no charge. J9 opens one test-mode billing-portal session on the sandbox and costs nothing in real money; no test account is ever charged for real.
- The ceiling falls whenever a row leaves the live suite with reviewed proof, because its takes go with it.

The other nightly limits follow the same rule (product owner, 14 Nov 16:36Z: "min cap for smoke tests to get truthful signal"). Each is derived as the minimum the chosen journeys need, not an approved budget, and none activates the nightly:

| Limit (`recurring-approval.json`) | Derived minimum per run | How |
|---|---|---|
| Fresh sign-ups | 8 | One per journey J1 to J8; J9 is long-lived |
| `takes` | 31 (30 while J7.a is held) | Sum of each case's catalog `minimumTakes`; every saved take is needed by a kept row |
| `starts` | 43 | The catalog's 42 `minimumStarts` plus J1.c's short-Stop take |
| `coachingRequests` | 31 (30 while J7.a is held), per journey | §6 above |
| `paidActionsUsd` | 0 | No real charge (J2 never pays; J9 uses test mode) |
| `runsPerPeriod` | 30 per 30 days | One run a night; a rerun is its own request |
| `identityReads`, `runCapRequests`, `windowMinutes`, `githubRunnerMinutes`, provider, cloud-agent and GitHub dollars | Not derivable yet | Every measured run in `case-costs.json` (R4C, R5) left rows NOT RUN, so its counts and times are lower bounds, and the journeys merge cases differently. Each is set from the first complete baseline run on the deployed build (item 15 in the PR), at the measured value with no margin, and the dollar caps need a measured unit price |

Period caps are the per-run minimum times the runs per period. A limit stays unset rather than guessed, and the nightly stays refused until every limit is set and the product owner activates it.
