# AHT redesign: a nightly regression suite for after MVP launch

Date: 14 November 2026. Main `897117b` (#1858). Design and coverage map only. Row-by-row map: [`coverage-map.v1.json`](coverage-map.v1.json), regenerated from the catalog by [`build_map.py`](build_map.py) (`python3 docs/aht-nightly/build_map.py . docs/aht-nightly/coverage-map.v1.json`).


## Framework (Akin, 14 Nov)

There is no target count. Each live case is a full user journey, oriented to MVP launch, run nightly after launch so that an upgrade that breaks something is caught. Every area is covered end to end, billing included. No test exists just to have a test: a check stays live only when a faster test can't catch the same break.

## The short version

- **9 live journeys replace the 15 cases.** Two are new: the payment wall and checkout on production (J2), and an existing paying customer after an upgrade (J9).
- **Billing's full lifecycle is not an AHT.** The subscription suite (#1795, `tests/billing/user-journey/`) covers conversion, failed renewal and recovery, and cancellation to period end with real Stripe events in a test-mode sandbox, on its own schedule. The live J2 covers only what production adds.
- **Every catalog check has a home** (§2): most move unchanged, AHT-15's move onto a run-owned account, a few are strengthened, and AHT-03 rows that repeat the same check on the same code are consolidated. New checks cover short Stop, sign-out reads, the payment wall, checkout, deletion, feedback with no session and upgrade continuity.
- **Every known gap has a home** (§3, §4): a live leg or a named faster test. A faster test counts only once it fails on the deliberately broken behaviour and passes when restored.
- **Prerequisites, open decisions and run results are tracked in the PR and issues**, not in this design, so it doesn't go stale as they land.

## 1. The journeys

Every leg keeps its own rows and cleanup. The four invariants (`owner-bound`, `start-press-budget`, `no-cloud-stt`, `owned-pages-closed`) are asserted in every leg.

**Dependent legs.** A leg that needs an earlier leg's result is NOT RUN, not FAIL, when that leg failed: J1.b to J1.d need J1.a's take, J1.f needs J1.e's expiry, and J8.c needs J8.b's takes. J1.e needs only the account, so it runs even when J1.a failed. Every other leg is independent of the legs before it.

### Notes per journey

- **J1.** Expiry is the last practice leg because it ends service; deletion follows it. `history-preserved` runs in J1.d, before expiry, because the expired account sees no history under Akin's rule. Ending the trial is a production write that needs the product owner's explicit approval before it is built; with it, the service role ends the trial on the run-owned account only (`trial_expires_at` in the past, never `commercial_trial_granted_at`, never another account). The wall is checked twice: on the still-open session (reload and navigate, as a real user who never signs out would see it) and after a fresh sign-in. `trial-expired-server-refuses` calls the deployed endpoints directly with the account's own token. It doesn't duplicate the DB and contract tests: it checks that the deployed bodies refuse. J1 also needs #1858 deployed: the cancelled-load watchdog stopped an AHT-01 run as well as AHT-04.
- **J2.** It never completes a payment, so production takes no charge, but it is not free of side effects. Opening Checkout on production creates a live-mode Checkout Session for the run-owned email and writes checkout rows (`begin_account_checkout`, `record_account_checkout`) that don't cascade on account deletion, and an abandoned session stays payable until it expires. J2 stays disabled until a reviewed cleanup step expires the session through Stripe, settles the checkout operation through the existing RPCs and proves nothing is left. Conversion, a failed renewal and recovery, cancellation to period end, and deleting a paying account belong to #1795's suite in a sandbox (§3). #1795's `portal_expiry` journey asserts readable saved history after expiry, which the 14 Nov rule now forbids; it has to change with the requirements doc.
- **J3.** AHT-03's copies of rapid repeat, next start, numeric and probe-save rows are dropped; they run on the same code in J1 and J3.a. Its `same-target-repeat` and `analytics-repeat-opens-product` stay: the partial-fixture repeat is the only one that starts from a take with missed points. J3 also depends on the feedback fence, because AHT-02 writes feedback.
- **J5.a** runs first in its own fresh context so the model cache is cold. Until #1858 is deployed and J5.a has passed once, dispatch it alone so a known failure doesn't share a run. J5.c keeps both observers the gap ledger requires for GAP-05 (R5, and R4C with the same leave action) and reports the tab-close variant separately.
- **J7** shares one signup across three fresh contexts. Each leg asserts its own take by session id, so a take from an earlier leg can't satisfy a later one. The harness already refuses AHT-12 and AHT-14 until a same-context denial-then-grant and a bytes-received fault are qualified; those qualifications are what's missing, not the checks. J7.d deletes the account through the product during the trial, the common path; run cleanup still verifies nothing is left.
- **J8** depends on the feedback fence (#1859) and its runner wiring (#1860).
- **J9** reads only. It doesn't record, because transcript retention keeps only the newest session's transcript, and nightly takes would erode the seeded history and grow the account past adapter limits. The seed sessions are created once on a named earlier release and pinned. A new take after an upgrade is already covered by J1 to J8. J9 does not cover a browser tab left open across a deploy (stale code chunks, or a model cached by the old release). That needs a check around each release (§4), because a nightly run starts with a clean browser.

## 5. Recommended count: 9 live journeys

Nine because there are nine distinct things that can break for a customer and need a real browser on the deployed build:
1. First use through the wall.
2. Getting from the wall to payment.
3. Focus.
4. A bad save connection.
5. Leaving mid-flow.
6. Two places at once.
7. First-time setup failures.
8. Feedback.
9. Existing data after an upgrade.

Fewer would put unrelated stories in one run, so one failure, like a Stripe outage or a cold-start bug, would hide the others. More would repeat signup and model download for no new signal. The owner's ten-scenario design of 14 Nov splits 12, 13 and 14 into separate runs, but they share setup safely with fresh contexts, and that design has no billing or upgrade-continuity journey. The billing lifecycle is real coverage but not an AHT: it runs in a sandbox, on #1795's existing suite.
