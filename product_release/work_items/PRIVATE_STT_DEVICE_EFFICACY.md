## Acceptance protocol

1. Freeze the exact served frontend SHA, build/asset identities and target devices: a supported desktop, a physical iPhone/Safari, and a physical Android/Chrome. Record hardware class, OS, browser version, Private backend, consent and app mode. Treat emulation and headless Chromium as CI controls, not device proof. Keep the current J1/J3/J7 live approvals unchanged.
2. Run controlled **cold** setup on each device twice in separate clean profiles, Wi-Fi (record actual link/throughput) and the declared mobile throttling profile (pin down/up rate and round-trip latency before execution). Use the same pinned assets. Record model wire bytes observed on the worker path, optional runtime/total bytes separately, download time from first model request to final byte, and setup time from consent to Ready. Opaque, unmatched or missing transfer measurements are **HOLD**, not zero. Run the cold interruption and cache scenarios above.
3. Run at least **20 consecutive warm 30-second takes** on each device (record the actual duration; valid band 29–31 s). Define the sample plan up front. Time from the user’s Stop action to (a) visible Stop acknowledgement, suggested gate ≤250 ms, and (b) authoritative, finalized transcript for the same take, not an interim or first-nonempty signal. Require **at least 95% within 5 seconds** and report per-device nearest-rank p95, pass count, sample count and worst result. Report all failures and timeouts; do not discard slow, aborted or missing takes. A committed take has one distinct, owner-bound persisted result and can reopen. Any unexpected document reload, lost or duplicate save is a failure, even if the latency percentage passes. Scripted reloads for cache proof are a separate scenario.
4. For the liberal device tier, screen proposed artifacts at ≤200 MB of model files on phones and ≤350 MB on desktop. Those are package budgets, not a proof of browser RAM usage. Use the actual warmed product and other open tabs to check responsiveness; keep peak memory and relative sibling-tab responsiveness as explicit observations. Do not substitute GPU availability for a passed device run. Publish closed-form timings, counts, boolean assertions and build pins; no raw audio, transcript text or customer identifiers in shared receipts.
5. **Before candidate testing:** review the baseline receipt; no model candidate download or accuracy run while any required baseline evidence is **HOLD/NOT RUN**. The source pins, package budget and supported devices for the proposed candidate must be identified in advance. Confirm candidate runtime/download/cache requirements on the same device tier before comparing accuracy. Do not weaken the baseline, reuse a stale receipt or silently switch to Cloud.

### Offline receipt checker
`scripts/lib/privateSttDevicePreflight.mjs` validates the structure and thresholds of a future content-free receipt, bound to an expected source and served SHA. It returns `STRUCTURALLY_COMPLETE`, not `PASS`: reviewers still must authenticate exact device and network provenance, confirm the referenced observations, check the package and runtime budget, and verify sample integrity. False or absent facts hold. `tests/unit/privateSttDevicePreflight.test.js` exercises the rejection paths with synthetic fixtures only. It is not a collector, does not run or authorize journeys, and is not yet wired to any live or model-comparison entry point.
