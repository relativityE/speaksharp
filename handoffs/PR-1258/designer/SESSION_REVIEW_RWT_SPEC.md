# Saved-session review + Focus Points states: RWT build spec

> **Standalone.** Nothing outside this document is needed except the repository `relativityE/speaksharp@main` (read 25 Sep 2026). All layout, colour, copy and rules are here. No mockup file is referenced.
> **Two parts.** **A**: the Practice Loop review block, one shared component shown in two places for both products. **B**: the Focus Points rail's state presentation on the Session page.
> **Scope:** the current journey only. Crediting particular tools for improvement across sessions is **out of scope** until after RWT. This is not a second Analytics design.

---

## 0. Where each part appears

| Part | Page | Position | Products |
|---|---|---|---|
| **A: review block** | **Session page, `after`** | Slot B, the full-width ink band beside/above the Live transcript, rendered as soon as the review is generated after Mic Stop | Open Mic and Focus Points |
| **A: review block** | **Analytics → saved session** (`/analytics/:sessionId`) | First block on the page, above the Progress panel | Open Mic and Focus Points |
| **B: rail states** | **Session page, `after`** | Right rail, the Points card | Focus Points only |

**One review, generated once.** After Mic Stop, `get-ai-suggestions` generates the pair and saves it on the session row (`sessions.ai_suggestions`). The Session page renders it. The Analytics saved-session view renders **the same saved pair, unchanged**. The Analytics view never generates new coaching, never re-requests the review, and never recalculates the session to produce a different lesson.

## Part A: The Practice Loop review block

### A1. What exists today

| Surface | Shows the saved pair? | Source |
|---|---|---|
| Session page `after` (`components/session/AISuggestions.tsx`) | Yes: `What went well` + `Try this next run` | Generated by `get-ai-suggestions`, saved to `sessions.ai_suggestions` |
| Home resume band (`components/practice/lastSessionFix.ts`) | Only `what_to_try_next`, verbatim | Same column, read-only, fail-closed parser |
| **Analytics saved session** (`components/AnalyticsDashboard.tsx`, the `targetSession` branch) | **No** | — |

On the Analytics saved-session view today, the page stacks `ProgressPanel`, three stat cards, and a Transcript card. That card contains a grey box (`data-testid="session-detail-next-action"`) rendered from `next_action_signal` via `renderNextActionCopy` (a title plus a generic body). The user never sees the lesson the Session page gave them.

**Saved coaching contract (unchanged):** `{ version: 'gemini_coaching_v1', what_worked, what_to_try_next }`, each at most 6 words / 90 characters. **It has no evidence, quote or reason field.**

### A2. The change, a small diff

1. **Extract** the pair JSX from `AISuggestions.tsx` (the `ai-suggestions-pair` block) into `components/session/ReviewPair.tsx`.
   Props: `{ worked: string; next: string; evidence: string[] | null; onPractice: () => void; sessionLabel: string | null }`.
   `AISuggestions` renders `ReviewPair` with its existing values. **Session-page output must not change** apart from the evidence line (A5), which also appears there.
2. **Add a read-only parser** `readSessionReview(raw): { worked: string; next: string } | null` beside `readLastSessionFix`, with the same fail-closed rules: exact key set `['version','what_to_try_next','what_worked']`, `version === 'gemini_coaching_v1'`, both halves non-blank after trim. Read `ai_suggestions` for the target session the same way Home does. **Do not widen `PracticeSession`**, and do not undo `storage.ts` stripping the field.
3. **Analytics saved session:** render the ink band with `ReviewPair` first, above `ProgressPanel`.
4. **Remove** the grey `session-detail-next-action` box whenever the review block renders. Keep its integrity-error branch (`session-next-action-integrity-error`) for a completed session with no valid signal.
5. **No network call for coaching** from the Analytics view. No `get-ai-suggestions` request, no Retry, no Generate control. Each request spends a daily quota slot and sends the transcript to the provider.

### A3. Block anatomy (shared by both products)

Ink band: `#1c2333`, `border-radius: 13px`, `padding: 20px 22px 22px`. In order:

1. **Header row**, `justify-content: space-between`:
   - `PRACTICE LOOP REVIEW`, 12px/800, `letter-spacing: 0.09em`, `#ffb61f`.
   - Session label, 12px/700, `#9aa6bd`: `Session {n} · {product} · {d Mon}`, e.g. `Session 7 · Focus Points · 24 Sep`.
2. **`WHAT WENT WELL`** panel: `#262f42`, radius 12px, `padding: 12px 15px`. Eyebrow 11px/800, `letter-spacing: 0.1em`, `#9aa6bd`. Sentence = saved `what_worked`, 15px/600, `#eef1f7`.
3. **`TRY THIS NEXT RUN`** block, 12px below: `#ffb61f` fill, radius 12px, `padding: 18px 20px`. **This is the next practice action and the page's only yellow fill.**
   - Eyebrow 11px/800, `letter-spacing: 0.1em`, `#1c2333`.
   - Sentence = saved `what_to_try_next`, **verbatim**, 20px/800, `letter-spacing: -0.015em`, `line-height: 1.35`, `#1c2333`.
   - **Evidence** (A5): `margin-top: 14px; padding-top: 12px; border-top: 1px solid #c98f13`. Eyebrow `FROM THIS SESSION` 11px/800 `#1c2333`, then one to three lines at 14px/700 `#1c2333`, 4px apart.
   - **One practice action**, `margin-top: 16px`: `Practice again?`, `#1c2333` fill, `#ffffff` text, 15px/800, height 44px, `padding: 0 20px`, radius 10px. It opens the same product as the saved session: Open Mic → `/session`; Focus Points → the same point set, the behaviour `Retry this set` already has.

No other button, link or chip goes inside the band.

### A4. States

| Condition | Block |
|---|---|
| Valid saved review, evidence available | Header, `What went well`, `Try this next run` + evidence + action |
| Valid saved review, no evidence available | Same, without the evidence section (eyebrow and lines both absent) |
| **No valid saved review** (absent, malformed, legacy, wrong version) | Header row, then `No coaching was saved for this session.` at 17px/700 `#eef1f7`, then `Practice again?` as a **yellow** button (`#ffb61f` / `#1c2333`, same size). **No stand-in lesson**: do not substitute `next_action_signal` copy or any other generated sentence for `what_to_try_next`. No evidence section. |
| Session not completed | Block does not render. The existing not-completed text stays where it is. |

The Session page keeps its own loading / retrying / terminal states in `AISuggestions` exactly as they are. Only its success state uses `ReviewPair`.

### A5. The evidence section: `FROM THIS SESSION`

The saved coaching has no reason field, so the AI's reasoning cannot be shown. The evidence section shows **measurements saved with this session**, placed beside the advice. Its label is always `FROM THIS SESSION`, **never** `Because`, `Why`, `Reason` or `Based on`, and no copy may imply the AI's advice was caused by these numbers.

**The evidence source follows the saved session's product, not the page.** Build it from stored data only, in code, and never recompute metrics from a transcript.

#### A5.1 Open Mic: delivery evidence

Source: the session's stored `next_action_signal` (`reasonCode`, `metric`, `value`, `comparator`), validated with `validateNextActionSignal`. One line:

| `reasonCode` | Line (`{v}` = `value`) |
|---|---|
| `PACE_TOO_SLOW` | `{v} words a minute, under the 130–150 target.` |
| `PACE_TOO_FAST` | `{v} words a minute, over the 130–150 target.` |
| `HIGH_FILLER_RATE` | `above_target` → `{v} filler words a minute, above your target.` · `above_baseline` → `{v} filler words a minute, more than your usual.` |
| `EXTENDED_PAUSES` | `{v} long pauses in this run.` |
| `CLARITY_BELOW_BASELINE` | `Clarity was {v}%, below your usual.` |
| `ESTABLISH_BASELINE`, `ON_TRACK` | none. The evidence section is absent |

Format pace as an integer, filler rate to one decimal place, clarity as an integer. Take the 130–150 band from the same constant the pace stat card uses. Do not duplicate the literal.

#### A5.2 Focus Points: coverage and timing evidence

Source: **the saved point results for this session**. For each point: its status (`covered` / `partial` / not detected) and `coveredAtSec`. Also the run's `duration` and the saved pace guide (`minutes per point × points`) if one was set. **No filler, wpm or clarity figures**, because those are Open Mic's metrics.

Up to three lines, in this order, each omitted when empty:

| Line | Template | Example |
|---|---|---|
| Detected | `Detected: point {i} at {m:ss}` for each detected point, joined `, ` | `Detected: point 1 at 0:21, point 2 at 1:04.` |
| Partly detected | `Partly detected: point {i} at {m:ss}` joined `, ` | `Partly detected: point 2 at 1:04.` |
| Not detected | `Not detected: point {i}` joined `, ` | `Not detected: point 3.` |
| Timing | guide set → `{m:ss} against your {m:ss} guide.` · no guide → `{m:ss} run.` | `3:24 against your 3:00 guide.` |

Only four lines are listed because a point appears in exactly one of the first three. Merge to at most three rendered lines by dropping the timing line if all three status lines are present.

Rules:

- **"Not detected" reports what the matcher found, not what the speaker did.** Never `missed`, `skipped`, `didn't say`, `forgot`, `left out` or `never`. Point numbers only. Don't repeat the point's text here, because the rail already shows it.
- Point numbers are the user's configured order, 1-based, and match the rail.
- **If the session's point results were not saved**, or the check never resolved (Part B's `unavailable`), the evidence section is absent. Never infer coverage from the transcript on the Analytics view.
- **Dev check before build:** confirm the point results (status + `coveredAtSec`) and the pace guide are persisted with the session and readable on `/analytics/:sessionId`. The Session page `after` state currently derives coverage from the retained transcript. If the results are not persisted, **A5.2 is HOLD on Analytics** (the section is absent there) and ships only on the Session page. Do not add persistence under this spec without PM sign-off.

#### A5.3 Illustrative coaching, and the prompt

The coaching phrases in any mockup are **illustrative only**. The product always renders the saved phrases verbatim.

For Focus Points, the advice should help the speaker cover their chosen points (for example, pacing across points or making a point explicit earlier), but only where the saved point results and transcript support it. That is a **generation** concern, not a rendering one. **Dev check:** confirm `get-ai-suggestions` receives the session's points and their results for Focus Points sessions. If it does not, record it as a follow-up for PM. It does not block this UI change, and the UI must not rewrite or filter the saved phrases to compensate.

### A5.4 Build notes: gaps to close while building

1. **Telemetry: the Analytics view must not emit the Practice Loop receipt.** `AISuggestions` emits `emitPracticeLoop({ phase: 'rendered' … })`, `trackPracticeLoopReviewRendered()` and `markCompletionStage('review_rendered' | 'practice_loop_ready')`. These stay in `AISuggestions` and **must not move into `ReviewPair`**. Rendering a saved review on Analytics is a re-view, not a completion. Emitting there would count every revisit as a new review. If PM wants a re-view count, add one closed event, `saved_review_viewed { product, has_evidence }`, with no prose.
2. **Session label.** Use `Session {n}` only if the session row already carries a stable ordinal. Otherwise render `{product} · {d Mon}` (e.g. `Focus Points · 24 Sep`). Never compute the ordinal from the currently loaded history list, which is paged and would drift.
3. **`Practice again?` from Analytics, Focus Points.** It needs the saved point set (brief id + points + topic + pace guide). If the session row doesn't carry the brief id, the action opens the Focus Points setup **prefilled from the saved points** so the user confirms and goes. It never silently starts a different set. If the points aren't readable either, the action opens Focus Points setup empty. That case is marked HOLD in the journey table and still counts as one practice action.
4. **Headings.** The eyebrow `PRACTICE LOOP REVIEW` is an `h2` on Analytics (it is an `h3` inside the Session page shell today, so keep it there). `What went well` / `Try this next run` stay `h4`, as today. The live journey locates them by heading role.
5. **Responsive.** The band is full content width at every size. Below 768px: padding `16px`, the `Try this next run` sentence 18px, the session label drops under the eyebrow, and `Practice again?` goes full width. Tap target ≥44px. Tested at 320 / 375 / 768 / 1280 with no horizontal scroll.
6. **Evidence lines on the Session page** use the same builders (A5.1 / A5.2), reading the in-memory signal and coverage rows the page already holds. A result not yet resolved (Part B `checking`) means no Focus Points evidence yet. It appears when the rail reaches `ready`.

### A6. Open for PM, not built here

On Analytics, `ProgressPanel` still renders its own `Practice this next` sentence and accept button beneath the review block, so there are two next-practice actions. Suggestion: when the review block renders, `ProgressPanel` drops its sentence and button and keeps its direction/baseline lines. **Leave `ProgressPanel` unchanged until PM answers.** Its button records a linked repeat attempt, which belongs to the post-RWT cross-session work.

### A7. Acceptance checks

| # | Check |
|---|---|
| A-1 | For a session with a valid saved review, the Analytics block shows **exactly** the `what_worked` / `what_to_try_next` strings the Session page showed for that session, in both products |
| A-2 | Opening `/analytics/:sessionId` makes **no** `get-ai-suggestions` request and renders no Retry/Generate control |
| A-3 | `Try this next run` is the only yellow fill on the Analytics view when a review exists, and `Practice again?` is the only action inside the band |
| A-4 | Every evidence section is headed `FROM THIS SESSION`. The strings `Because`, `Why this`, `Reason` and `Based on` appear nowhere in the band |
| A-5 | Open Mic evidence matches A5.1 for each `reasonCode` and is absent for `ESTABLISH_BASELINE` / `ON_TRACK` |
| A-6 | Focus Points evidence contains only detected/partly/not-detected point numbers with timestamps, and duration against guide. It contains no wpm, filler or clarity figure |
| A-7 | No Focus Points evidence or rail string contains `missed`, `skipped`, `didn't say`, `forgot`, `left out` or `never` |
| A-8 | With no valid saved review, the band shows `No coaching was saved for this session.` and a yellow `Practice again?`, with no substituted lesson and no evidence |
| A-9 | A malformed, legacy or wrong-version `ai_suggestions` value renders the no-review state, never partial text |
| A-10 | The grey `session-detail-next-action` box is absent whenever the block renders |
| A-11 | The Session page's review renders identically before and after the `ReviewPair` extraction, apart from the added evidence section |

## Part B: Focus Points rail states (Session page, `after`)

Applies to `components/session/FocusPointsRail.tsx`, and to `CoverageRail.tsx`, which must match. `CoverageRail` currently uses `bg-regression opacity-70` for a missing point, which is retired.

### B1. One meaning per colour

| Colour (token) | Meaning | When |
|---|---|---|
| Grey: `neutral-border-strong` ring, `neutral-muted` numeral | Not checked yet | `before` and `during` (solid ring). **Checking** after Stop (dashed ring) |
| Purple: `focus-points` ring + numeral on `focus-points-ground` row | Next up | `during` only |
| Green: `progress-bar` fill, white ✓ | Detected | `after`, **always with a timestamp** |
| Amber: `signature` ring, `signature-text` glyph, `signature-ground` / `signature-border` row | Look again: partly detected or not detected | `after` only, never before a result |

**Colour is never the only signal.** Today each row's status word is `sr-only`. **Make it visible** on every row with a result or a check in progress, 12px/800, directly under the label:

- Detected → `Detected at 0:21` in `status`, then the saved covering quote in italic 13px `neutral-secondary`
- Partly detected → `Partly detected at 1:04` in `signature-text`
- Not detected → `Not detected` in `signature-text`
- Checking → `Checking…` in `neutral-secondary`

Screen-reader output must stay equivalent: keep the `sr-only` word or give the visible word the same text.

### B2. The final "Not detected" treatment

- **Marker:** amber ring with **the point's own numeral**, not ✕. ✕ reads as "wrong", which a keyword matcher cannot establish. The numeral keeps the point identifiable, and colour plus the visible word carry the status.
- **Row:** `signature-ground` fill, 1px `signature-border`, radius 10px. Label 15px/700 `neutral-body`, not struck through.
- **Words:** `Not detected`, nothing else on the row. It must not assert or imply the speaker never said the point. The strings in A-7 are banned here too.
- **The limit note, once per card**, below the list, 13px `neutral-secondary`: `We look for your point's words in what you said. If you covered it differently, we may not spot it.` Render it only when at least one row is partly or not detected. **Remove** the per-row sentence (`focus-point-{i}-not-detected`) and move the note from above the list to below it.
- **Detected rows:** label `neutral-body`, **no strike-through**.
- Eyebrow once results exist: `WHAT WE DETECTED` (unchanged).

### B3. The visible pending state: Checking

Today, after Stop and before coverage resolves, rows fall back to plain grey under the `Points to cover` eyebrow, which looks the same as `before`.

| State | Eyebrow | Rows | Card text |
|---|---|---|---|
| **Checking**: after Stop, result not yet resolved | `CHECKING YOUR POINTS` | 2px **dashed** `neutral-border-strong` ring + numeral; `Checking…` under each label | none |
| **Unavailable**: final, no evidence will arrive | `POINTS TO COVER` | Solid grey ring + numeral, no status word | Under the eyebrow, 15px/700 `neutral-body`: `We couldn't check your points this time. Your session is saved.` |
| **Checked** | `WHAT WE DETECTED` | Per B1/B2 | Limit note, conditionally (B2) |

- `Retry this set` / `Start a new set` remain available in all three.
- **Never show green or amber while checking.** A result that appears early and then changes is the trust failure the conservative matcher is there to prevent.
- No spinner. The eyebrow and the per-row word are the whole progress indication.
- If `coveragePending` currently covers both "still resolving" and "will never resolve", replace it with `coverageStatus: 'checking' | 'unavailable' | 'ready'` so the two states render differently.

### B4. Acceptance checks

| # | Check |
|---|---|
| B-1 | Every `after` row with a result shows a visible status word. None relies on colour alone |
| B-2 | A not-detected marker is an amber ring containing the point's numeral. No ✕ renders on the rail |
| B-3 | The detection-limit sentence appears at most once per card, below the list, and only when a row is partly or not detected |
| B-4 | After Stop and before resolution: eyebrow `CHECKING YOUR POINTS`, every row dashed with `Checking…` |
| B-5 | No green or amber marker renders before a result exists |
| B-6 | The unavailable state shows the saved-session sentence and no negative claim on any row |
| B-7 | `CoverageRail` and `FocusPointsRail` render the same marker, colour and word for the same status. `bg-regression` appears in neither |
| B-8 | Detected labels are not struck through |
